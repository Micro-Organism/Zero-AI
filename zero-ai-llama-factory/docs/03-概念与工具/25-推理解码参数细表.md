# 25 · 推理解码参数细表

## 本章目标

集中理解「生成时」常用解码参数：它们改变回答的风格与随机性，**不改变已训练好的权重**。概念期建立调参直觉；具体默认值与参数名以官方 Arguments / 生成参数章节为准。

> 参数百科：https://llamafactory.readthedocs.io/zh-cn/latest/advanced/arguments.html  
> 推理入口：https://llamafactory.readthedocs.io/zh-cn/latest/getting_started/inference.html

## 生成 vs 训练（先分清）

| | 训练（SFT 等） | 推理生成 |
|--|----------------|----------|
| 改什么 | 权重（或 adapter） | 一般不改权重 |
| 关键旋钮 | lr、epoch、lora_rank… | temperature、top_p、max_new_tokens… |
| 目标 | 学会分布 | 从分布中采样/搜索出一段文本 |

同一 adapter，解码参数不同，观感可以差很多——调聊天效果前先确认不是「没加载 adapter」。

## 常用参数直觉表

| 参数（常见名） | 作用直觉 | 调大 | 调小 |
|----------------|----------|------|------|
| `max_new_tokens` / 最大新 token | 最多生成多长 | 更长回答，更慢更费显存 | 更短，可能截断 |
| `temperature` | 随机性温度 | 更发散、更「创意」 | 更稳、更确定 |
| `top_p`（nucleus） | 从概率质量前 p 的集合里采样 | 候选更多、更活 | 更收、更稳 |
| `top_k` | 只从概率最高的 k 个里采样 | 更宽 | 更窄 |
| `repetition_penalty` | 抑制重复 | 减轻车轱辘话（过大可能怪） | 更易重复 |
| `do_sample` | 是否采样 | true：随机采样；false：常配合贪心/束搜索 | — |
| `num_beams` | 束搜索宽度 | 更偏搜索、更稳但更慢（视实现） | 1 近乎贪心 |
| `length_penalty` | 束搜索长度偏好 | 偏好更长/更短（视符号约定） | — |

不同后端（HF / vLLM）支持的参数集合可能略有差异；以当前推理引擎文档为准。

## 实用组合（经验起点，非绝对）

| 场景 | 起点直觉 |
|------|----------|
| 事实问答 / 要稳 | 较低 `temperature`（如 ~0.1–0.5），适度 `top_p` |
| 头脑风暴 / 文案 | 较高 `temperature`，`top_p` 放宽 |
| 易重复 | 略增 `repetition_penalty`，检查是否数据本身重复 |
| 总被截断 | 增大 `max_new_tokens`，同时注意显存 |
| 对比实验 | **一次只改一个解码参数** |

## 和 WebUI / CLI 的关系

- WebUI **对话**页通常可调部分生成参数（界面项随版本变化）。
- YAML / API 推理时，生成参数出现在生成参数组或请求体中。
- 评估（`predict_with_generate`）也会走生成路径，解码设置会影响 BLEU/ROUGE 与观感。

## 纸面练习

1. 客服机器人要「少胡编」，你会优先动 temperature 还是 max_new_tokens？为什么？  
2. 模型反复复读同一句，除了惩罚项，还应回头检查训练数据的什么问题？  
3. 为什么说「先确认加载了 adapter，再调 temperature」？

## 检查点

- [ ] 能区分训练超参与解码参数
- [ ] 能说明 temperature / top_p / max_new_tokens 的方向性影响
- [ ] 知道调聊天效果时应单变量对比

## 常见坑

- 没加载微调权重，却在疯狂调 temperature
- temperature 与 top_p 同时拉满，输出不可控还难以归因
- `max_new_tokens` 过大导致推理 OOM
- 用评测分数优化解码，却忘了业务要的是格式与拒答策略
