# AI 工程师作品集与求职规划

> 一句话定位：用六个可运行、可复现、可解释、可交付的项目证明能力，而不是用框架关键词或课程数量证明“学过”。

## 快速概览

| 证据 | 证明能力 | 必须展示 |
|---|---|---|
| ML Baseline | 数据、指标、误差分析 | split、baseline、slice、报告 |
| PyTorch Project | DL 训练与诊断 | loop、checkpoint、曲线、复现 |
| LLM Fine-tuning | 数据到模型后训练 | base 对比、回归、显存/成本 |
| RAG/Agent Service | AI 系统设计 | retrieval eval、trace、安全工具 |
| Eval/Deployment Study | 工程交付 | registry、SLO、canary、rollback |
| Specialization | 深度与方向 | CV/多模态/RL/机器人等一项闭环 |

## 核心技术要点与扩展谱系

| 层级 | 技术要点 | 解决的问题 | 前置知识 | 掌握标准 | 关联章节 |
|---|---|---|---|---|---|
| 必会 | Python/SQL coding、data/debugging | 证明基础工程执行力 | `01`、`19` | 能限时完成并测试数据任务 | `01`、`19` |
| 必会 | ML/DL fundamentals、metric/error analysis | 证明算法判断而非调 API | `02-05` | 能白板解释并诊断一次实验 | `03-05`、`14` |
| 必会 | system design：RAG/Agent/serving/MLOps | 证明端到端交付能力 | LLM、后端 | 能设计 SLO、权限、观测和回滚 | `12`、`15`、`20` |
| 必会 | project evidence：README、data/model card、reproduction | 让个人贡献可验证 | 至少三个项目 | 新环境可运行且结果可追溯 | 全路线 |
| 进阶 | ablation、performance/cost study、failure postmortem | 展示研究与高级工程深度 | 评测、性能 | 能用证据解释取舍和失败 | `14`、`16`、`21` |

## 纵向：从学习到录用的完整闭环

```text
岗位族采样 -> 技能频率/深度分析 -> 自评 -> 项目选题 -> baseline
          -> 实验/评测 -> 工程交付 -> 文档/演示 -> 模拟面试
          -> 定向投递 -> 面试反馈归因 -> 项目与知识补强
```

| 招聘信号 | 弱证据 | 强证据 |
|---|---|---|
| 熟悉 PyTorch | 简历列出关键词 | 独立训练循环、诊断和 checkpoint 恢复 |
| 熟悉 LLM 微调 | 跑过 WebUI | 数据审计、base 对比、回归与资源报告 |
| 熟悉 RAG/Agent | 聊天 Demo | 检索标注集、trace、权限和失败恢复 |
| 工程能力 | 能启动 API | SLO、评测门禁、观测、canary、rollback |
| 算法能力 | 背诵模型结构 | 假设、基线、消融、错误归因和取舍 |

## 横向：与其他技术的连接

- **利用 Java 优势**：展示事务、权限、稳定性和平台架构，但训练/数据/推理主证据使用 Python。
- **连接业务价值**：每个指标解释对用户、成本或风险的意义，不只报 benchmark。
- **连接研究能力**：能阅读论文、复现关键点并做消融，不需要追逐所有新论文。
- **连接工程能力**：README、环境锁定、测试、Docker、监控和 runbook 是模型之外的可信度。
- **连接沟通能力**：项目报告要讲问题、方案、对比、结论、限制；能诚实解释失败。
- **连接宏观方向**：先投 AI/LLM 工程、算法工程、平台/推理等相邻岗位，再按反馈调整深度。

## 技术对比与选型

### 岗位族对比

| 岗位族 | 核心深度 | 工程要求 | 作品集重点 |
|---|---|---|---|
| ML/算法工程师 | ML/DL、实验、领域算法 | 中到高 | baseline、训练、评测、专项 |
| LLM 后训练工程师 | SFT/PEFT/对齐、数据 | 高 | 微调、评测、性能 |
| RAG/Agent 工程师 | 检索、workflow、工具安全 | 很高 | 端到端服务与 trace |
| 推理/MLOps 平台 | serving、GPU、分布式、SRE | 很高 | 性能、发布、监控、成本 |
| CV/多模态工程师 | 视觉/跨模态模型与数据 | 高 | CV/VLM 专项 |
| 机器人学习工程师 | RL、控制、ROS、仿真 | 很高且跨学科 | 仿真到实机闭环 |

### 项目选择原则

| 选题 | 是否推荐 | 原因 |
|---|---:|---|
| 通用聊天壳 | 否 | 难证明数据、算法和工程深度 |
| 有真实评测的垂类任务 | 是 | 能展示闭环和业务判断 |
| 复刻热门框架 Demo | 仅作起点 | 需加入 baseline、消融和工程化 |
| 超大而无法复现的项目 | 否 | 面试无法验证个人贡献 |
| 小而完整的可复现系统 | 是 | 容易讲清决策、失败和边界 |

## Step by Step

1. 收集 30-50 个目标岗位，按岗位族统计 Python、PyTorch、LLM、数据、部署和专项要求。
2. 用 `00-能力地图` 自评，将缺口分为“必须、加分、暂缓”。
3. 完成六个证据项目；每个项目只承担清晰能力目标，避免一个仓库塞入所有技术。
4. 为每个项目写 README、架构、数据卡、实验表、失败案例、启动命令与限制。
5. 录制 3-5 分钟演示或准备截图，同时确保无演示也能从报告判断质量。
6. 为每个项目准备 2 分钟概述、10 分钟深挖和追问：为什么这样选、失败过什么、怎样改。
7. 补 Python 编码、SQL/数据、ML/DL 原理和 AI 系统设计面试题。
8. 每周复盘投递 -> 筛选 -> 一面 -> 后续漏斗，只依据重复反馈修改路线。

## 最小项目与验收标准

**最终产物：六项目 AI 工程师作品集**

| 项目 | 最低验收 |
|---|---|
| ML Baseline | 无泄漏 split、交叉验证、slice、误差报告 |
| PyTorch Project | 自定义数据、训练/验证、恢复、诊断 |
| LLM Fine-tuning | 数据卡、base vs tuned、回归、导出/成本 |
| RAG/Agent | retrieval eval、引用、工具权限、trace |
| Eval/Deployment | 质量/性能门禁、Docker、监控、canary/rollback |
| Specialization | 一个方向从数据到部署/仿真的完整闭环 |

每个项目还必须满足：新环境可运行、依赖锁定、核心逻辑有测试、无密钥/隐私数据、结果可追溯、明确不适用边界。

## 常见误区与面试达标

- 误区：用“精通”替代证据，列十几个框架却讲不清一次失败。
- 误区：完全按某一家公司的 JD 学习，能力无法迁移。
- 误区：只做模型不做数据、评测和部署，或只做 API 不理解模型。
- 面试达标：能白板解释数据 -> 训练 -> 评测 -> 服务 -> 监控完整链路。
- 面试达标：能在性能、成本、质量、安全和交付周期之间做具体取舍。
