# 数据工程与特征工程路线

> 一句话定位：把原始数据变成可验证、可追溯、可复用的训练与推理输入；数据工程从第一个项目开始，不是模型训练后的附属工作。

## 快速概览
| 层次 | 技术 | 产物 | 风险 |
|---|---|---|---|
| 获取 | API、SQL、文件、消息流 | raw immutable data | 权限、丢失、重复 |
| 处理 | Python/SQL、batch/stream | cleaned dataset | schema 漂移、泄漏 |
| 质量 | constraints、profiling、tests | quality report | 静默错误 |
| 版本 | snapshot、lineage、catalog | dataset version | 无法复现 |
| 特征 | transform、feature store | offline/online features | 训练服务偏差 |

| 层级 | 技术要点 | 解决的问题 | 前置知识 | 掌握标准 | 关联章节 |
|---|---|---|---|---|---|

| 必会 | NumPy、Pandas/Polars、DuckDB | 单机列式处理与分析 | Python | 能按内存/吞吐选择工具 | `01` |

| 必会 | schema/constraint/profiling、data contract | 发现静默质量错误 | 测试 | 质量失败能阻断 pipeline | `14-15` |

## 纵向：从原理到交付的完整闭环
```text
业务实体/时间定义 -> 源登记 -> 原始快照 -> schema/质量检查
                 -> 清洗/连接/特征 -> 按时间或主体切分 -> 版本冻结
                 -> 训练/评测 -> 在线特征或批预测 -> 漂移/回填/删除
```
| 环节 | 必须回答 | 验收 |
|---|---|---|
| 源 | 谁拥有、许可和更新频率是什么 | source registry |
| Schema | 类型、主键、时间和空值语义 | contract tests |
| 变换 | 是否幂等，可否重跑 | deterministic output |
| 切分 | 特征在预测时是否真实可得 | point-in-time join |
| 发布 | 数据和模型如何追溯 | lineage + checksum |

## 横向：与其他技术的连接
- **与 ML**：标签、切分和特征泄漏比换模型更常决定结果。
- **与 LLM**：预训练语料、SFT 数据、RAG 文档都需要相同的数据治理原则。
- **与 MLOps**：数据版本是模型 lineage 的起点，schema 变化应阻止坏版本发布。
- **与安全**：最小权限、脱敏、保留与删除策略必须进入 pipeline。
- **与 Java**：业务库由业务服务负责；Python 通过只读快照、事件或契约接口消费。

## 技术对比与选型
| 对比 | 方案 A | 方案 B | 选择依据 |
|---|---|---|---|
| Pandas vs Polars | 生态成熟 | 列式/并行友好 | 数据量、团队生态 |
| CSV vs Parquet | 通用可读 | 类型/压缩/列裁剪 | 交换/分析训练 |
| Batch vs Stream | 简单可重放 | 低延迟持续处理 | 时效与复杂度 |
| ETL vs ELT | 入库前变换 | 仓内变换 | 平台与治理边界 |
| Feature Store vs 普通表 | 复用与在线一致 | 简单低成本 | 多模型复用需求 |

### 规模与编排选型

| 层级 | 典型工具 | 何时采用 | 不应采用的情况 |
|---|---|---|---|
| 单机列式处理 | Pandas、Polars、DuckDB | 可放入单机，开发/分析优先 | 不需要为“像大数据”而上集群 |
| 分布式 Batch | Spark 类引擎 | 单机内存/时间不可接受，已有集群 | 数据小、团队无运维能力 |
| 工作流编排 | Airflow、Dagster、Prefect 类 | 多任务依赖、调度、重试和 backfill | 单个可重复脚本已足够 |
| 数据/实验版本 | snapshot、DVC/lakeFS 类思路 | 数据持续变化且需重现实验 | 只记录文件名、不保存 checksum |
| 流处理 | Kafka + Flink/Spark Streaming 类 | 业务确需秒/分钟级新鲜度 | 小时/天级 batch 已满足目标 |

选型顺序是先证明数据量、时效或依赖复杂度超出单机能力，再引入分布式和编排平台。工具升级必须保留同一 schema、质量断言、幂等语义和 lineage。

## Step by Step
1. 用 SQL 构造带时间窗口的训练样本，写出主键与标签时间定义。
2. 将 CSV 转 Parquet，比较大小、读取时间和类型稳定性。
3. 为 schema、唯一性、范围、空值和分布写自动检查。
4. 实现幂等 batch pipeline，支持指定日期重跑和 backfill。
5. 做 point-in-time join，证明没有使用预测时刻之后的数据。
6. 固定数据版本、checksum、代码和参数，重建同一训练集。
7. 模拟 schema 漂移和迟到数据，验证告警与修复流程。
8. 输出 data card、lineage 图和数据删除流程。

## 最小项目与验收标准
**项目：可复现的训练数据流水线**
| 验收项 | 过关标准 |
|---|---|
| SQL | 时间语义明确，无多对多意外膨胀 |
| 质量 | schema/范围/重复/分布检查自动化 |
| 重跑 | 同输入和版本产生同 checksum |
| 泄漏 | point-in-time 验证和切分说明完整 |
| 血缘 | 能追溯到源、变换、数据集和模型 |
| 治理 | 权限、PII、保留和删除策略明确 |

## 常见误区与面试达标
- 误区：在 notebook 手工改数据，却无法重建训练集。
- 误区：随机切分时间数据，或把未来统计写入历史特征。
- 面试达标：能解释幂等、partition、event time、lineage 和 point-in-time correctness。
