# Zero AI Career Workspace 设计说明

> 状态：已完成产品设计确认，等待书面规格复核后进入实施计划。
>
> 日期：2026-08-03
>
> 子项目：`zero-ai-interview`

## 1. 项目概述

`zero-ai-interview` 是面向个人使用的 AI 求职工作台。第一版聚焦人工智能工程师岗位，通过持续积累招聘信息、候选人简历和个人职业材料，帮助用户维护可信的主简历、分析岗位要求、识别能力差距、生成岗位定制简历并完成导出或打印。

产品不是简单的 AI 对话壳，也不是只有文件列表的资料库。系统以结构化职业事实为数据底座，以可追溯的 AI 任务连接简历、招聘、匹配和成长分析模块。

## 2. 用户与产品边界

### 2.1 第一版用户

第一版只服务一个个人用户：

- 提供登录、退出和个人资料功能；
- 所有主要业务数据保留 `user_id`；
- 数据访问接口按用户隔离；
- 不开放注册；
- 为以后扩展多用户保留结构，但不实现租户、团队和计费。

### 2.2 核心目标

| 目标 | 验收结果 |
|---|---|
| 积累招聘资料 | 能导入、解析、检索、编辑、分页和归档招聘信息 |
| 建立个人事实库 | 能维护工作、项目、教育、技能、证书和成果 |
| 形成可信主简历 | 主简历可编辑、版本化、比较和恢复 |
| 完成岗位匹配 | 每条岗位要求都能关联简历证据、缺口和风险 |
| 生成定制简历 | 从主简历派生，不虚构、不污染主简历 |
| 支持交付 | 能预览、下载、导出 PDF/DOCX/Markdown/JSON 并进行 A4 打印 |
| 支持长期成长 | 能统计技能频率、归纳岗位族并形成学习建议 |

### 2.3 第一版不包含

- 公开注册和第三方登录；
- 多人协作、招聘人员和面试官角色；
- 付费、配额和订阅；
- 自动抓取招聘网站；
- 企业 ATS 或招聘流程管理；
- 自动投递简历；
- 无人工确认的自动简历改写；
- 自动执行外部 Agent 工具。

## 3. 核心设计原则

1. **职业事实优先**：工作、项目、教育和成果是可信事实，AI 只能整理和表达，不能凭空创造。
2. **原始资料可追溯**：保存原文件、原始文本、AI 结构化草稿和人工确认结果。
3. **主简历与定制简历分离**：定制简历从指定主简历版本派生，不反向覆盖主简历。
4. **AI 结果默认是草稿**：正式写入职业档案或简历前必须人工确认。
5. **失败可恢复**：解析、AI 生成和导出均为持久化任务，支持查看进度、失败原因和重试。
6. **模块化单体**：第一版保持部署简单，同时通过清晰模块边界为未来拆分服务预留空间。
7. **框架可替换**：模型、数据库、文件存储和文档解析通过适配层封装。

## 5. 核心业务流程

### 5.1 求职匹配主闭环

```text
录入招聘信息
  -> 保存原文和附件
  -> 解析岗位结构
  -> AI 提取岗位要求
  -> 人工校对要求
  -> 选择主简历版本
  -> 逐项映射简历证据
  -> 计算匹配度、缺口和风险
  -> 补充个人事实或确认暂不具备
  -> 生成岗位定制简历草稿
  -> 人工编辑和事实检查
  -> 生成正式版本
  -> PDF/DOCX/Markdown/JSON 导出或 A4 打印
```

### 5.2 简历导入流程

```text
上传文件/粘贴文本
  -> 文件安全校验与哈希去重
  -> 创建解析任务
  -> 提取文本/OCR
  -> 保存原始文本
  -> AI 提取结构化经历草稿
  -> 用户逐项确认、修改或忽略
  -> 写入经历素材库
  -> 选择是否生成新的主简历版本
```

### 5.3 招聘信息导入流程

```text
上传图片/PDF/DOCX 或粘贴 JD
  -> 解析原文
  -> 识别公司与岗位基础信息
  -> 提取必备、加分、软实力和企业限定要求
  -> 用户校对
  -> 保存招聘记录与岗位要求
  -> 可选创建求职匹配项目
```

### 5.4 AI 引导完善主简历

系统基于完整性检查和岗位证据需求生成问题，例如：

- 项目解决了什么业务问题；
- 用户具体承担了什么工作；
- 使用了哪些技术，为什么这样选；
- 有哪些基线、指标、规模和效果；
- 出现过什么失败，如何修复；
- 哪些表述缺少可验证证据。

用户回答先保存为补充草稿。只有用户确认后，内容才进入经历素材或主简历版本。

## 6. 模块设计

### 6.1 `auth`

- 单用户初始化；
- 登录、退出、当前用户；
- 密码修改；
- HttpOnly Cookie 会话；
- 未来多用户扩展所需的用户主键和数据隔离。

### 6.2 `resume`

- 职业档案；
- 工作经历、项目经历、教育、技能、证书、成果；
- 主简历组成与排序；
- 简历版本快照；
- 定制简历派生；
- 模板选择、预览、事实检查和导出。

### 6.3 `recruitment`

- 公司档案；
- 招聘信息和原始 JD；
- 岗位族、级别、地点、来源和状态；
- 必备技能、加分技能、软实力、企业限定；
- 标签、搜索、筛选、排序、分页和批量操作。

### 6.4 `matching`

- 创建求职匹配项目；
- 固定关联一个招聘记录和一个主简历版本；
- 要求与证据逐项映射；
- 匹配分、证据强度、缺口和风险；
- 生成补充问题、定制摘要和定制简历；
- 保留人工覆盖及其原因。

### 6.5 `insight`

- 招聘技能频率；
- 必备与加分技能分布；
- 岗位族归纳；
- 个人能力覆盖率；
- 重复出现的能力缺口；
- 学习建议和学习任务草稿。

### 6.6 `file` 与 `task`

- 文件上传、预览、下载、归档和软删除；
- 文件哈希和内容指纹去重；
- 解析、OCR、AI、导入和导出任务；
- 进度、结果、失败原因、重试次数和取消状态；
- 任务恢复和异常任务处理。

### 6.7 `ai`

- OpenAI 兼容服务配置；
- Base URL、模型名、密钥引用和生成参数；
- 连接测试；
- Prompt 模板和版本；
- JSON Schema 结构化输出；
- 原始响应、解析结果、耗时和 token 使用记录；
- 超时、限流、错误格式和模型切换。

### 6.8 `system`

- 标签与字典；
- 文件策略；
- 任务管理；
- 模型与 Prompt 管理；
- 操作日志；
- 回收站；
- 预留系统状态页。

## 8. 匹配与生成规则

### 8.1 岗位要求分类

- `required`：岗位硬性要求；
- `preferred`：加分项；
- `soft_skill`：沟通、协作、文档等；
- `company_specific`：学历、党员、地点等企业限定；
- `responsibility`：岗位职责；
- `domain`：行业经验要求。

### 8.2 证据强度

| 等级 | 定义 |
|---|---|
| 0 | 无证据 |
| 1 | 仅在技能列表声明 |
| 2 | 有学习或 Demo 经历 |
| 3 | 有完整项目和个人贡献 |
| 4 | 有指标、规模、复盘或生产证据 |

### 8.3 匹配分

第一版使用可解释的确定性加权规则，不让 LLM 直接给出最终分数：

- 必备要求权重高于加分项；
- 企业限定项单独展示，不与技术能力混淆；
- 每项分数来源于证据强度和用户确认结果；
- AI 可以建议证据映射，但用户可以修改；
- 总分同时展示权重明细和缺失项，不只显示一个百分比。

### 8.4 定制简历生成约束

- 只能选择、重排、压缩和改写已有职业事实；
- 新增事实必须先写入经历素材库并经用户确认；
- 每段生成内容保存来源实体 ID；
- 导出前执行日期、公司、岗位、指标和技能事实检查；
- 无证据的关键词只进入学习建议，不进入正式简历。

## 10. 前端设计

### 10.1 技术栈

- React；
- TypeScript；
- Vite；
- Ant Design；
- React Router；
- TanStack Query；

- 左侧主菜单、顶部上下文操作区、主内容区；
- 表格页面保持筛选、分页、批量操作和详情抽屉一致；
- AI 任务显示阶段、进度、耗时和可重试操作；

- 删除、覆盖、恢复和正式发布需要明确确认；
- 长文本、中文、移动视口和 A4 打印不得重叠或截断；
- 图标使用现有图标库，不手绘 SVG。

## 12. 数据库与配置

实现时先对用户提供的数据库地址进行非破坏性连接探测，确认数据库类型后创建项目数据库。数据库连接串仅进入未提交的本地环境变量。

本地开发应保留可独立启动的数据库配置，避免远程数据库不可用时无法运行测试。数据库迁移由 Alembic 管理，不依赖手工建表。

模型配置使用 OpenAI 兼容协议，至少包含：

- 显示名称；
- Base URL；
- API Key 密钥引用；
- 模型名；
- 超时；
- 最大重试；
- 温度和最大输出；
- 是否启用；
- 连接测试状态。

## 13. 异常处理

| 场景 | 行为 |
|---|---|
| 文件类型或大小不合法 | 上传前后双重校验并显示原因 |
| 文档只能部分解析 | 保存部分结果，标记待校对 |
| AI 超时或限流 | 指数退避重试，可切换模型后重跑 |
| AI 输出不符合 Schema | 保存原响应，尝试修复，失败后人工录入 |
| 重复导入 | 通过文件哈希和内容指纹提示合并或保留副本 |
| 编辑版本冲突 | 返回冲突错误，允许刷新、比较或另存版本 |
| 导出失败 | 保留简历版本，仅重试导出任务 |
| 任务中断 | 标记异常，支持继续或重新执行 |
| 数据库不可用 | 阻止写入，不显示虚假成功状态 |
| 认证过期 | 跳转登录并保留原地址 |

## 14. 安全设计

- 密码使用安全哈希；
- 认证 Cookie 使用 HttpOnly，并按部署环境配置 Secure 和 SameSite；
- API Key、数据库密码不写入数据库明文、代码、文档或 Git；
- 上传文件校验扩展名、MIME、大小、路径和文件名；
- 禁止可执行文件和路径穿越；
- 简历和招聘正文作为不可信数据，不能覆盖系统指令；
- AI 不执行正文中包含的外部操作指令；
- 模型日志避免重复保存完整敏感文本；
- 永久删除、版本恢复和导出写入审计日志；
- 所有业务查询检查 `user_id`。

- A4 打印和长中文文本布局。

### 15.3 端到端验收

必须跑通：

```text
登录
-> 导入一份招聘信息
-> 校对岗位要求
-> 创建或导入主简历
-> 创建匹配项目
-> 查看逐项证据和能力缺口
-> 生成定制简历草稿
-> 人工编辑并确认
-> 导出 PDF/DOCX/Markdown/JSON
-> 浏览器 A4 打印
```

### 15.4 非功能验收

- 桌面和移动视口无文本重叠；
- 列表分页和筛选状态稳定；
- 长任务不阻塞普通 API；
- 失败任务可重试；
- 新环境可通过文档启动；
- 无密钥、密码、个人隐私样本进入 Git；
- 数据库迁移可重复执行；
- README 包含架构、配置、启动和验证命令。

## 16. 实施顺序

详细任务将在实施计划中展开，整体顺序为：

1. 子项目骨架、开发配置和登录；
2. 数据库模型、迁移和通用 CRUD；
3. 文件、任务和导入解析；
4. 简历中心；
5. 招聘中心；
6. AI Provider 与结构化提取；
7. 匹配中心与可解释评分；
8. 定制简历、模板、导出和打印；
9. 洞察与学习计划；
10. 系统管理、测试、文档和端到端验证。

## 17. 成功标准

当用户能够持续加入新的简历和招聘信息，并通过同一套事实数据完成岗位分析、主简历完善、岗位匹配、定制简历生成和可验证导出时，第一版即达到产品目标。
